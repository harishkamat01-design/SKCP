# Decision Log

**Date:** 2026-07-26

---

# Decision 1

## Title

Learn Database Concepts Through the Business

### Decision

Every database concept will first be understood using the real operations of Shree Kundodari Cement Products before introducing technical terminology.

### Reason

Business-first learning creates stronger understanding and long-term retention compared to memorizing definitions.

---

# Decision 2

## Title

Adopt the SKCP Learning Bridge™

### Decision

A permanent "SKCP Learning Bridge™" approach will be used throughout Module 3.

Every business question should map directly to its corresponding database concept.

Example:

Business Question → Database Answer

Customer → Customer Table

Order → Orders Table

Payment → Payments Table

Stock → Inventory Table

### Reason

This approach connects theory with real business operations and makes abstract database concepts easier to understand.

---

# Decision 3

## Title

Assign Unique IDs to All Business Objects

### Decision

Every major business object in SKCP will have its own unique identifier.

Examples include:

- Customer ID
- Product ID
- Supplier ID
- Order ID
- Payment ID
- Inventory ID
- Production Batch ID

### Reason

Unique identifiers simplify relationships, improve data integrity, and support scalable database design.

---

# Decision 4

## Title

Interview-Oriented Learning Repository

### Decision

Alongside project documentation, a dedicated Interview Preparation repository will be maintained.

The repository will contain:

- Common interview questions
- Practical answers
- SKCP-based examples
- Revision notes

### Reason

Learning should prepare both the SKCP project and future technical interviews without requiring duplicate effort.

---

# Decision 5

## Title

Documentation at the End of Learning Sessions

### Decision

Documentation will continue to be completed after meaningful learning milestones rather than after every individual concept.

### Reason

This keeps learning uninterrupted while ensuring documentation remains accurate, organized, and complete.

---

# Decision 6

## Title

GitHub as the Single Source of Truth

### Decision

The GitHub repository will be treated as the official project reference.

Future documentation updates will be generated by comparing the latest GitHub state with newly learned concepts.

### Reason

This avoids duplicate work, prevents inconsistencies, and makes End-of-Day documentation significantly faster.

---

# Decision 7

## Title

Business Objects Before Database Tables

### Decision

Database tables will only be designed after identifying the real business objects inside the factory.

Examples include:

- Customer
- Supplier
- Product
- Inventory
- Production
- Order
- Payment

### Reason

A database should model the real business rather than screens or software components.

# Decision 08

## Title

Business Owns Data

### Decision

Data will always be stored with the business object that logically owns it rather than where it is most convenient to store.

### Reason

Correct ownership reduces duplication, improves maintainability and accurately reflects real business operations.

---

# Decision 09

## Title

Use Junction Tables for Many-to-Many Relationships

### Decision

Whenever a Many-to-Many relationship is discovered during business analysis, a dedicated Junction Table will be introduced.

### Reason

Relational databases cannot directly represent Many-to-Many relationships while maintaining normalization.

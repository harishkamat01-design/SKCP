# 1. What is a DTO?

DTO stands for **Data Transfer Object**.

A DTO is a Java object used to transfer data between different layers of an application.

In a Spring Boot REST API:

Client → Controller → DTO → Service → Entity → Repository → Database

DTOs are NOT database tables.

DTOs are NOT JPA entities.

DTOs are objects designed specifically for communication between the client and application layers.

---

# 2. Why do we need DTOs?

Before DTOs, our controller directly accepted and returned the Customer entity.

The architecture was:
```text
Postman / Frontend  
↓  
Customer Entity  
↓  
CustomerService  
↓  
CustomerRepository  
↓  
Database
```
This created tight coupling between the API and database model.

The database entity represents how data is stored.

The API should represent what the client is allowed to send and receive.

DTOs create a separation between these two responsibilities.

---

# 3. SKCP Business Analogy

Think about our father's cement block business.

The factory maintains an internal register containing detailed customer information.

This is similar to:

Customer Entity

A customer, however, fills only the information that the business wants to collect.

This is similar to:

CustomerCreateRequest

The customer should not directly control internal information such as:

- Customer ID
- Status
- Created At

Therefore:
```text
Customer Form  
↓  
Employee checks/translates it  
↓  
Factory Register
```
In software:
```text
Request DTO  
↓  
Mapper  
↓  
Customer Entity
```
The DTO acts like the controlled customer form.

# 4. Entity vs DTO

## Entity

`Customer.java` represents the database/customer record.

It contains:

- customerId
- customerName
- mobileNumber
- alternateMobile
- address
- village
- city
- pincode
- gstNumber
- remarks
- status
- createdAt

The entity represents the persistent database record.

## Request DTO

`CustomerCreateRequest` contains only fields that the client is allowed to provide.

It contains:

- customerName
- mobileNumber
- alternateMobile
- address
- village
- city
- pincode
- gstNumber
- remarks

It does NOT contain:

- customerId
- status
- createdAt

Why?

`customerId` → generated by the database.

`status` → controlled by backend business logic.

`createdAt` → generated automatically by the backend using `@PrePersist`.

# 6. CustomerCreateRequest

Used when creating a new customer.

Flow:

```text
                Postman JSON
                    ↓
                CustomerCreateRequest
                    ↓
                CustomerService
                    ↓
                CustomerMapper
                    ↓
                Customer Entity

Example:
{
  "customerName": "Ganesh Shanbhag",
  "mobileNumber": "9000000001",
  "alternateMobile": "8000000001",
  "address": "Near Ganapati Temple, Main Road",
  "village": "Chitragi",
  "city": "Kumta",
  "pincode": "581343",
  "gstNumber": "20ABCDF1234F1Z0",
  "remarks": "DTO test customer"
}

```
The client does NOT send:

* customerId
* status
* createdAt

These are controlled by the backend.

# 7. CustomerUpdateRequest

Used when updating an existing customer.

Flow:

```text
Postman JSON
      ↓
CustomerUpdateRequest
      ↓
CustomerService
      ↓
CustomerMapper
      ↓
Existing Customer Entity
```
The update request contains editable customer information.

It does NOT allow the client to directly control:
* customerId
* status
* createdAt

This protects important backend-controlled fields.

```text

```

```text

└── response/
```

# 9. CustomerResponse

`CustomerResponse` is used when the client needs the complete customer information.

It contains fields such as:

```text
customerId
customerName
mobileNumber
alternateMobile
address
village
city
pincode
gstNumber
remarks
status
createdAt
```
Notice that response DTOs can contain backend-generated information.

For example:
```text
customerId
status
createdAt
```

These were intentionally excluded from request DTOs but are included in the response.

Why?

Because: 
```text 
Client → Backend 
```
and 
```text
Backend → Client
```
have different requirements.

---
# 10. CustomerSummaryResponse

A summary response is used when we don't need all customer information.

For example:

```text
GET /api/customers
```
Instead of sending every detail of every customer, we return only:
```text
customerId
customerName
mobileNumber
village
city
status
```
This is lighter and more appropriate for customer lists/search results.

Architecture:
```text
Customer Entity
      ↓
CustomerSummaryResponse
      ↓
Customer List / Search
```
Detailed fields such as:
```text
alternateMobile
address
pincode
gstNumber
remarks
createdAt
```
are intentionally excluded.
---

# 11.  Why separate Create, Update and Response DTOs?

We could technically create one huge DTO.

But that would mix different responsibilities.

Instead:
```text
CustomerCreateRequest
        ↓
What can the client send while creating?

CustomerUpdateRequest
        ↓
What can the client change?

CustomerResponse
        ↓
What information should the backend return?

CustomerSummaryResponse
        ↓
What minimum information is required for lists/search?
```
This gives us a clear API contract.

# 14. What changed in CustomerController?
### Before DTOs 

The controller accepted the entity:

```text
@RequestBody Customer customer
```

The controller also returned:
```text
ResponseEntity<Customer>
```
Therefore the API was directly exposing the database entity.

---
### After DTOs
The controller accepts:
```text
@Valid @RequestBody CustomerCreateRequest request
```
and:
```text
@Valid @RequestBody CustomerUpdateRequest request
```
The controller returns:
```text
CustomerResponse
```
or:
```text
CustomerSummaryResponse
```
The controller no longer imports:   

```text
import com.skcp.entity.Customer;
```
This is an important architectural improvement.

---
# 15. What changed in CustomerService?
Before DTOs:

```text
CustomerService
    ↓
Customer Entity
    ↓
Repository
```
After DTOs:
```text
CustomerService
    ↓
Request DTO
    ↓
Mapper
    ↓
Entity
    ↓
Repository
```
And for responses:
```text
Repository
    ↓
Entity
    ↓
Mapper
    ↓
Response DTO    
```
The service became the central point where business operations work with DTOs and entities through the mapper.

# 16. What did NOT change?
Introducing DTOs did NOT require us to redesign the database.

These remain:
```text
Customer Entity
CustomerRepository
Database table
Database save/find/delete operations
```
**The DTO architecture is mainly a communication boundary**.

---
# 17. Why DTOs are important in production software
DTOs provide:
### 1. Encapsulation
Database implementation details are not directly exposed.
### 2. API stability
Database entities can change internally without necessarily changing the API contract.
### 3. Security
Clients cannot directly send backend-controlled fields.
### 4. Validation
Request DTOs can contain validation rules.

Example:
```text
@NotBlank
@Size
@Pattern
```
### 5. Different views of the same entity
The same Customer entity can have:
```text
CustomerCreateRequest
CustomerUpdateRequest
CustomerResponse
CustomerSummaryResponse
```
depending on the requirement.
### 6. Maintainability
The API contract and database model remain separate.

# 18. DTOs and Validation
One important connection with the next phases:
```text
Postman
   ↓
Request DTO
   ↓
Validation
   ↓
Service
```
For example: In the **CustomerCreateRequest.java**

```text
@NotBlank
private String customerName;
```
and
```text
@Pattern(
    regexp = "^[6-9]\\d{9}$"
)
private String mobileNumber;
```
The validation belongs on the request **DTO**, because the DTO represents what the client is allowed to send.

This is one reason DTOs come before our Validation discussion.

# 19. DTOs and ModelMapper
After DTO architecture, we introduced **ModelMapper**.

The responsibility is different.

**DTO**

Defines:

> "What data should cross the API boundary?"

**Mapper**

Defines:
> "How do I convert between the API object and internal entity?"

Therefore:

```text
DTO Architecture
       ↓
  defines the objects
         ↓
    ModelMapper
           ↓
      simplifies conversion between objects
```
**DTOs and ModelMapper are related, but they are NOT the same thing.**

---
# 20. Our CustomerMapper
Our current mapper uses ModelMapper:

```text
public Customer toEntity(CustomerCreateRequest request) {
    return modelMapper.map(request, Customer.class);
}
```
This means:
```text
                CustomerCreateRequest
                        ↓
                    ModelMapper
                        ↓
                Customer Entity
```
For responses:
```text
public CustomerResponse toResponse(Customer customer) {
    return modelMapper.map(customer, CustomerResponse.class);
}
```
Therefore:

```text
Customer Entity
        ↓
     ModelMapper
        ↓
CustomerResponse
```
The Mapper is the bridge.

# 21. Important clarification: DTO does NOT create database relationships

This is an important lesson we discussed.

Suppose later SKCP has:

```text
Customer
Order
Payment
Product
OrderItem
```
and these tables have relationships.

DTOs do NOT create those database relationships.

For example:
```text
        Customer
        │
        │ customer_id
        ▼
        Order
```
Order
The actual relationship is implemented through:

```text
Database foreign keys
+
JPA entity relationships
```
such as:
```text
@ManyToOne
@JoinColumn(...)
```
**DTOs only decide how that relationship is represented when data crosses the API boundary.**

---

# 22. SKCP Example of Future Relationship
Suppose:

```text
Customer
customer_id = 16
```
creates:
```text
Order
order_id = 101
customer_id = 16
```
The database relationship is:

```text
Customer 16
     ↑
     │ foreign key
     │
Order 101
```
A DTO might represent that information as:
```text
{
    "orderId": 101,
    "customerId": 16,
    "orderDate": "2026-08-09"
}
```
The DTO is **not creating the relationship.**

The database/JPA mapping creates and maintains the relationship.

This distinction is important for interviews.

# 23. Enterprise Best Practices
Good DTO architecture generally follows these principles:


```text
1. Do not expose JPA entities directly through REST APIs.

2. Use request DTOs for incoming data.

3. Use response DTOs for outgoing data.

4. Keep client-controlled and backend-controlled fields separate.

5. Use different DTOs when different use cases require different data.

6. Keep validation rules on request DTOs where appropriate.

7. Keep mapping logic outside the controller.

8. Keep business logic inside the service layer.

9. Keep database access inside the repository layer.

10. Avoid putting database-specific behavior into DTOs.
```
---

# 24. Interview Answer – Short Version
Question:

Why do we use DTOs instead of directly exposing entities?

Answer:

> DTO stands for Data Transfer Object. We use DTOs to separate the API contract from the persistence model. Request DTOs control what data clients can send, while response DTOs control what data the API exposes. This improves encapsulation, security, validation, maintainability, and API stability. In SKCP, `CustomerCreateRequest` is converted into the `Customer` entity through the mapper, and the entity is converted back into `CustomerResponse` before being returned to the client.

---

# 25. Interview Answer – SKCP Example

>In our SKCP application, initially the Customer entity was directly exposed through the REST controller. We refactored this to use DTOs. `CustomerCreateRequest` and `CustomerUpdateRequest` handle incoming data, while `CustomerResponse` and `CustomerSummaryResponse` handle outgoing data. The service layer works with the business logic, and the mapper converts between DTOs and entities. This prevents the client from directly controlling fields such as customer ID, status, and creation timestamp and keeps our database model independent from the API contract.

# 26. Common Mistakes

*Mistake 1*

Using:
```text
@RequestBody Customer customer
```
when the API should use a request DTO.

---
*Mistake 2*

Returning:
```text
Customer
```
 directly from the REST controller.

---

*Mistake 3*

Allowing the client to send:


```text
customerId
createdAt
status
```
when these should be controlled by the backend.

---

*Mistake 4*

Putting mapping logic inside the controller:


```text
customer.setCustomerName(request.getCustomerName());
```


The mapping responsibility belongs in the mapper.

---
*Mistake 5*

Putting business logic inside DTOs.

DTOs should primarily represent data transfer.

# 30. Final Mental Model

Imagine SKCP as a factory.

```text
                CUSTOMER
                │
                │ fills form
                ▼
                REQUEST DTO
                │
                │ translator
                ▼
                MAPPER
                │
                ▼
                ENTITY
                │
                │ factory records it
                ▼
                DATABASE
                │
                │ retrieve
                ▼
                ENTITY
                │
                │ translator
                ▼
                RESPONSE DTO
                │
                ▼
                CLIENT
```

The client never walks directly into the database register.
It submits a form.

The backend translates the form into its internal representation.

The database stores the internal representation.

When information comes back, the backend translates it into a response designed for the client.

That is the essence of DTO architecture.

# 31. Lesson Learned
DTO architecture taught us an important enterprise software principle:
>#### Separate what the system stores from what the system communicates.

This separation gives us flexibility.

Our database can evolve.

Our API can evolve.

Our business logic can evolve.

And these changes do not necessarily have to break each other.

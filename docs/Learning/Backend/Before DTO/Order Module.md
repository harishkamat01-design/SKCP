# Module Purpose

The Order module is the entry point of the complete Sales workflow.

Its responsibility is to store the Order Header information only.

An Order represents the customer's purchase request before delivery.

Actual ordered products are stored separately in the **OrderItem** module.

This follows enterprise ERP architecture where:

```
Customer
     │
     ▼
 Order (Header)
     │
     ▼
OrderItem (Product Details)
```

---

# Database Design

```sql
CREATE TABLE orders
(
    order_id SERIAL PRIMARY KEY,

    customer_id INT NOT NULL,

    order_date DATE NOT NULL,

    expected_delivery_date DATE,

    order_status VARCHAR(15)
        NOT NULL
        DEFAULT 'PENDING'
        CHECK
        (
            order_status IN
            (
                'PENDING',
                'PARTIAL',
                'COMPLETED',
                'CANCELLED'
            )
        ),

    remarks TEXT,

    created_at TIMESTAMP
        NOT NULL
        DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT fk_order_customer
        FOREIGN KEY (customer_id)
        REFERENCES customer(customer_id)
);
```

---

# Database Explanation

## order_id

Primary Key

Uniquely identifies every customer order.

---

## customer_id

Foreign Key

Connects the Order to the Customer.

Relationship

```
Customer (1)
      │
      ▼
Order (Many)
```

---

## order_date

Stores when customer placed the order.

Mandatory field.

---

## expected_delivery_date

Expected delivery date committed to customer.

Optional because delivery date may be decided later.

---

## order_status

Business Status

Allowed values

```
PENDING
PARTIAL
COMPLETED
CANCELLED
```

Default

```
PENDING
```

---

## remarks

Stores additional business notes.

Example

```
Deliver before 10 AM
```

---

## created_at

Audit field.

Automatically generated by PostgreSQL.

# Enterprise Design Decisions

## Decision 1

Order Header and Order Items are separated.

Reason

One Order can contain multiple products.

Industry Standard

ERP Systems

SAP

Oracle

Microsoft Dynamics

---

## Decision 2

Customer Relationship

```
Customer (1)

↓

Orders (Many)
```

Reason

One customer places many orders.

---

## Decision 3

ResponseEntity used

Instead of returning Entity directly.

Benefits

Proper Status Codes

REST Standard

Easy frontend integration

---

## Decision 4

Business Logic kept inside Service Layer

Controller remains thin.

---

## Decision 5

Repository contains zero business logic.

Only Database access.
